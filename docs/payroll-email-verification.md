# Winsalot Corp. payroll email verification

Verified October 2, 2026. Changes are prepared on `codex/payroll-paid-email`. No production migration, live payroll update, live email, merge or deployment was performed.

## Before the change

`markPayrollPaidAction` and `markLeadgenPayrollPaidAction` only updated their payroll table, inserted a `marked_paid` audit entry and revalidated pages. Neither called an email sender. Production payroll database triggers only protected finalized records or maintained timestamps; they did not send email. No automatic payroll email template or payroll delivery history existed.

## Shared trigger and notification ownership

1. Admin invokes the existing Paid action from either CRM. Existing Admin authorization remains required.
2. The action updates its existing record only if it is still Approved, and returns the finalized stored row. Failed updates and lost concurrent transitions do not send.
3. The existing payment audit event is recorded. Both actions call the SAME server-only `sendPayrollPaidEmail` workflow.
4. That workflow reserves one row in `payroll_email_notifications`, owned by Winsalot payroll. Database unique constraints cover BOTH agent + period and source record. Two CRM records for the same agent/period cannot reserve separate emails, even concurrently. Henry and Goodness have the same authenticated user ID in both production CRM user tables.
5. The first finalized record to reserve that shared claim supplies the payroll amount and note. The email uses the stored agent address/currency and the existing Resend client. Both sources use the same payroll sender category: default `Winsalot Corp. <info@winsalotcorp.com>`, optional `PAYROLL_EMAIL_FROM`, existing shared Reply-To.
6. One shared template includes the pay period, actual payment date, payment method, wage, bonus, internet allowance, other additions, holiday pay, deductions, final payable total and Notes for agent. The existing `admin_notes` column is explicitly the agent-facing note in the current UI. Internal adjustment and reopening reasons are excluded by an explicit field allowlist.
7. There is no existing separately addressable statement route. The email links to the applicable authenticated My Pay page, where the existing statement can be printed or saved as PDF. No public payroll link or duplicate statement system is introduced.
8. Provider acceptance/failure is recorded in the shared notification row. The existing signed Resend webhook records delivery events there. A provider tag identifies the claim even if the webhook arrives before the send response is logged. Conditional updates prevent an older event or send response from overwriting a newer delivery status.

Existing payroll storage is still `crm_payroll` and `leadgen_payroll`; this change does not consolidate those financial records or aggregate attendance. It centralizes the email workflow and notification history around the finalized applicable record. If both CRMs supplied work information already included in that record, its stored final total is used without recomputation. Separate finalized records with different totals for the same period are not summed automatically; the shared guard suppresses a second notification.

## Reopening, failures and duplicate suppression

The shared claim survives reopening and repeated saves. Repaid records do not automatically resend. A historically reopened record without a claim gets a suppressed notification entry rather than a blind new email. Explicit provider rejection is Failed; ambiguous exceptions after a send attempt are Unknown. Neither result rolls back a successful payment or automatically retries. Resend also receives an agent/period idempotency key. Failure to reserve a durable notification row prevents sending.

Admin opens Payroll → View Audit Log to see the original payment audit entries and the shared Winsalot payroll email status, recipient, Resend ID, timestamp and error. Both CRM views display the same shared notification history for matching authorized agent/period records. Sent means provider accepted; Delivered requires a verified event. Pending/Unknown should be reviewed before any manual resend.

## Security and preservation

The notification table has RLS enabled, no public/client access and explicit service-role SELECT/INSERT/UPDATE grants. Server-only history reads are restricted to agent/period records returned by each existing Admin page's authenticated RLS query. No existing payroll/attendance/audit tables, records, grants or policies are migrated or rewritten. Existing audit trails are retained; there is one new notification history for Winsalot payroll, not one per CRM.
